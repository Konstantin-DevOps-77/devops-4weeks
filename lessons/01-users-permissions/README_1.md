## 1. Зачем это нужно в работе

В первый же рабочий месяц ты встретишь такие тикеты:

- «После деплоя сервис не стартует, в логе `Permission denied`».
- «Разработчики не могут править файлы друг друга в общей папке».
- «Скрипт деплоя скопировали на сервер, он не запускается».
- «Нужно дать новому коллеге право перезапускать один сервис, но не больше».

За каждым стоят **пользователи, группы и права доступа**. Эта тема встречается в каждой инфраструктуре и в каждом собеседовании: на DevOps-позиции почти всегда спрашивают про права, `sudo` и принцип наименьших привилегий.

Принцип наименьших привилегий (least privilege) короткий: **у каждого пользователя и у каждой программы должно быть ровно столько прав, сколько нужно для работы, и ни одним больше.**

В этом уроке ты разберёшься в теме и потренируешься на **кейсах**: это заготовленные сломанные ситуации, оформленные как рабочие тикеты. Ты сам диагностируешь, чинишь и пишешь отчёт, как это принято в команде.

## 2. Правила безопасности для этого урока

> [!WARNING]
> Это твой настоящий сервер с работающим VPN. Ошибка с правами может закрыть тебе вход по SSH. Поэтому:
>
> - Экспериментируй только на **лабораторных объектах**: пользователи с именем `lab-...`, папки `/srv/lab` и `~/practice`.
> - Команды с `-R` (`chmod -R`, `chown -R`) выполняй **только** внутри `/srv/lab` и `~/practice`. Рекурсивная смена прав на `/root`, `/etc`, `/home` или `/` сломает вход на сервер.
> - Не трогай `/etc/ssh`, не меняй пользователя `root`, не отключай вход root по паролю.
> - Файлы `sudo` правим **только** через `visudo`. Не редактируй `/etc/sudoers` в `nano`.
> - Содержимое `/etc/shadow` (хэши паролей) никуда не копируй, в том числе в `answers.md`.
> - `chmod 777` не используем никогда. Если тебе кажется, что нужен `777`, значит, ты не нашёл настоящую причину.
> - Если после твоих действий вход по SSH перестал работать, не паникуй: в панели Aeza есть вкладка **VNC** (вход через браузер). Зайди через неё и напиши наставнику.

## 3. Два инструмента для анализа: grep и cut

Для разбора системных файлов нужны два маленьких инструмента. Они понадобятся тебе во всём курсе. Слова ЗАГЛАВНЫМИ буквами в шаблонах команд (`ФАЙЛ`, `ИМЯ`, `ГРУППА`) нужно заменить на своё значение: это не готовые команды.

**`grep`** ищет строки, содержащие заданный текст:

| Команда | Что делает |
|---|---|
| `grep СЛОВО ФАЙЛ` | выводит строки файла, где есть слово |
| `grep -n СЛОВО ФАЙЛ` | то же, с номерами строк |
| `grep -i СЛОВО ФАЙЛ` | без учёта регистра букв |
| `grep -v СЛОВО ФАЙЛ` | наоборот: строки, где слова **нет** |
| `grep -c СЛОВО ФАЙЛ` | только количество подходящих строк |
| `КОМАНДА \| grep СЛОВО` | искать в выводе другой команды |

**`cut`** вырезает из строк нужные столбцы:

| Команда | Что делает |
|---|---|
| `cut -d: -f1 ФАЙЛ` | разделитель `:` (`-d:`), вывести первый столбец (`-f1`) |
| `cut -d: -f1,3 ФАЙЛ` | первый и третий столбцы |

### Попробуй

Это безопасное чтение:

```bash
grep -n "^root" /etc/passwd
grep -c "bash" /etc/passwd
grep -c "nologin" /etc/passwd
cut -d: -f1 /etc/passwd | head -n 5
cut -d: -f1,3 /etc/passwd | head -n 3
```

Знак `^` в `"^root"` означает «в начале строки». Он нужен, чтобы не находить, например, `nobody:...:/root`.

## 4. Пользователи и группы

**Пользователь** это учётная запись с числовым номером **UID** (user ID). **Группа** это набор пользователей с номером **GID**. Права на файлы выдаются не людям, а владельцу файла, группе файла и «всем остальным».

У каждого пользователя есть:

- **основная группа** (создаётся вместе с ним, обычно с тем же именем);
- **дополнительные группы** (в них его добавляют, чтобы дать доступ к чему-то общему).

Три вида пользователей:

| Вид | UID | Для чего | Оболочка |
|---|---|---|---|
| `root` | `0` | администратор, может всё | `/bin/bash` |
| Системные (служебные) | меньше `1000` | запускают службы: `www-data`, `sshd`, `postgres` | `/usr/sbin/nologin` (войти нельзя) |
| Обычные | `1000` и больше | живые люди | `/bin/bash` |

Служебные пользователи нужны для безопасности. Если веб-сервер взломают, злоумышленник получит права `www-data`, а не `root`.

### Команды для разведки

| Команда | Что показывает |
|---|---|
| `whoami` | под каким пользователем ты работаешь |
| `id` | твой UID, GID и все группы |
| `id ИМЯ` | то же для другого пользователя |
| `groups ИМЯ` | только группы пользователя |
| `who` | кто сейчас подключён к серверу |
| `last -n 5` | последние 5 входов в систему |
| `getent passwd ИМЯ` | строка про пользователя из базы системы |
| `getent group ИМЯ` | строка про группу и её участников |

### Попробуй

```bash
whoami
id
id nobody
groups root
getent passwd root
getent group sudo
last -n 5
```

`nobody` это специальный пользователь без прав, он нам пригодится для проверок («а чужой не прочитает?»).

## 5. Файлы /etc/passwd, /etc/group и /etc/shadow

Информация о пользователях лежит в трёх текстовых файлах. Ты уже читал `/etc/passwd` в уроке 0, теперь разберём его строки.

**`/etc/passwd`**: список пользователей. Каждая строка делится двоеточиями на семь полей:

```
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
```

| Поле | Значение |
|---|---|
| `daemon` | имя пользователя |
| `x` | пароль хранится не здесь, а в `/etc/shadow` |
| `1` | UID |
| `1` | GID основной группы |
| `daemon` | комментарий (полное имя) |
| `/usr/sbin` | домашняя папка |
| `/usr/sbin/nologin` | оболочка: `nologin` значит «войти по логину нельзя» |

**`/etc/group`**: список групп. Формат `имя:x:GID:участники`, например `sudo:x:27:devops`.

**`/etc/shadow`**: хэши паролей. Файл читает только `root`:

```bash
ls -l /etc/passwd /etc/group /etc/shadow
```

Обрати внимание на разницу в правах. `/etc/passwd` читать может любой (программам нужно переводить номера в имена), а `/etc/shadow` закрыт: иначе любой пользователь мог бы забрать хэши паролей и подбирать их. Это хороший пример принципа наименьших привилегий.

> [!CAUTION]
> Не выводи содержимое `/etc/shadow` на экран и тем более не копируй его в отчёты и чаты. Это хэши паролей.

## 6. Управление пользователями и группами

| Команда | Что делает |
|---|---|
| `adduser ИМЯ` | создать обычного пользователя (интерактивно: домашняя папка, пароль, вопросы) |
| `adduser --disabled-password --gecos "" ИМЯ` | создать без пароля и без вопросов (для технических целей) |
| `adduser --system --group --no-create-home ИМЯ` | создать **служебного** пользователя (без входа и без домашней папки) |
| `groupadd ГРУППА` | создать группу |
| `usermod -aG ГРУППА ИМЯ` | **добавить** пользователя в группу |
| `passwd ИМЯ` | сменить пароль |
| `su - ИМЯ` | войти как другой пользователь (`exit` вернёт назад) |
| `deluser --remove-home ИМЯ` | удалить пользователя вместе с домашней папкой |
| `delgroup ГРУППА` | удалить группу |

В Ubuntu есть пара команд `adduser` и `useradd`. **`adduser`** это удобная надстройка для людей: сама создаёт домашнюю папку и группу, спрашивает пароль. **`useradd`** низкоуровневая, для скриптов: без явных опций ничего лишнего не делает. Для ручной работы используй `adduser`.

> [!CAUTION]
> **`usermod -aG`: опция `-a` обязательна.** Без неё команда `usermod -G ГРУППА ИМЯ` **заменяет** все дополнительные группы пользователя на указанную. Если так «добавить в группу», пользователь молча теряет `sudo` и остальные группы. Это одна из классических ошибок, после которой админ теряет доступ к серверу.

Изменение групп вступает в силу при **новом** входе пользователя.

### Попробуй

Создадим временного пользователя и убедимся в опасности `-G` без `-a`:

```bash
groupadd lab-demo1
groupadd lab-demo2
adduser --disabled-password --gecos "" lab-try
usermod -aG lab-demo1 lab-try
id lab-try
usermod -aG lab-demo2 lab-try
id lab-try
usermod -G lab-demo1 lab-try
id lab-try
```

После второй команды у `lab-try` обе группы. После третьей (`-G` без `-a`) группа `lab-demo2` **пропала**. Запомни это ощущение.

Входим как этот пользователь и выходим:

```bash
su - lab-try
whoami
pwd
exit
```

Знак `-` в `su -` означает «полноценный вход»: загрузится окружение пользователя и ты окажешься в его домашней папке.

Оставь `lab-try` пока на месте: он понадобится в следующих разделах для проверок.

## 7. Права доступа: читаем rwx

Вспомни вывод `ls -l`:

```
-rwxr-x--- 1 root lab-team 86 Oct 13 17:51 run.sh
```

Первая колонка состоит из **десяти** символов:

```
-   rwx   r-x   ---
│    │     │     │
│    │     │     └── права для всех остальных (others)
│    │     └──────── права для группы файла (group)
│    └────────────── права для владельца (user)
└─────────────────── тип: - файл, d папка, l ссылка
```

Три вида прав:

| Буква | Для файла | Для каталога |
|---|---|---|
| `r` (read) | читать содержимое | **смотреть список имён** внутри (`ls`) |
| `w` (write) | менять содержимое | **создавать, переименовывать, удалять** файлы внутри (нужно ещё и `x`) |
| `x` (execute) | запускать как программу | **заходить** (`cd`) и обращаться к файлам внутри по имени |

Система проверяет по порядку: если ты **владелец**, действуют права владельца. Иначе, если ты **в группе** файла, права группы. Иначе права «остальных». Права срабатывают по первому совпадению, а не складываются.

### Числовая запись

Каждое право имеет вес: `r` = 4, `w` = 2, `x` = 1. Сумма для каждой тройки даёт одну цифру:

| Тройка | Расчёт | Цифра |
|---|---|---|
| `rwx` | 4+2+1 | 7 |
| `rw-` | 4+2 | 6 |
| `r-x` | 4+1 | 5 |
| `r--` | 4 | 4 |
| `---` | 0 | 0 |

Права `rwxr-x---` в числах: `750`. Самые частые режимы:

| Режим | Запись | Для чего |
|---|---|---|
| `644` | `rw-r--r--` | обычные файлы: владелец пишет, остальные читают |
| `600` | `rw-------` | **секреты, пароли, приватные ключи**: только владелец |
| `640` | `rw-r-----` | конфиги, которые читает служба из группы файла |
| `755` | `rwxr-xr-x` | программы, скрипты, публичные каталоги |
| `750` | `rwxr-x---` | каталоги и программы только для владельца и группы |
| `700` | `rwx------` | личные каталоги, `~/.ssh` |

### Посмотреть права числом

```bash
stat -c '%A %a %U:%G %n' /etc/passwd /etc/shadow /root
```

Формат выводит: права буквами, права числом, владельца и группу, имя.

## 8. Меняем права: chmod, chown, chgrp

**Менять права** (`chmod`) может владелец файла или `root`. **Менять владельца** (`chown`) может только `root`.

### chmod

Числами:

```bash
chmod 640 ФАЙЛ
```

Буквами: кому (`u` владелец, `g` группа, `o` остальные, `a` все), что сделать (`+` добавить, `-` убрать, `=` задать точно), какие права:

| Команда | Что делает |
|---|---|
| `chmod u+x ФАЙЛ` | владельцу добавить запуск |
| `chmod g-w ФАЙЛ` | у группы убрать запись |
| `chmod o-rwx ФАЙЛ` | у остальных убрать всё |
| `chmod a+r ФАЙЛ` | всем добавить чтение |
| `chmod u=rwx,g=rx,o= ФАЙЛ` | задать точно: `rwxr-x---` |

Опция `-R` применяет изменение ко всему содержимому папки. Это опасный инструмент, используй только в `/srv/lab` и `~/practice`.

### chown и chgrp

| Команда | Что делает |
|---|---|
| `chown ИМЯ ФАЙЛ` | сменить владельца |
| `chown ИМЯ:ГРУППА ФАЙЛ` | сменить владельца и группу сразу |
| `chown :ГРУППА ФАЙЛ` | сменить только группу |
| `chgrp ГРУППА ФАЙЛ` | сменить только группу |

### Попробуй: root обходит права

Это самая важная ловушка темы. Готовим лабораторную папку:

```bash
mkdir -p /srv/lab/demo
cd /srv/lab/demo
echo "hello" > file.txt
chmod 600 file.txt
ls -l file.txt
cat file.txt
sudo -u lab-try cat /srv/lab/demo/file.txt
```

`root` прочитал файл без проблем, а `lab-try` получил `Permission denied`. **`root` игнорирует права доступа.** Поэтому проверять, работает ли доступ, нужно **от имени нужного пользователя**: `sudo -u ПОЛЬЗОВАТЕЛЬ команда`. Фраза «у меня работает» после проверки под `root` ничего не значит. Типичный провал новичков и повод для шуток в команде.

Теперь откроем чтение:

```bash
chmod 644 file.txt
sudo -u lab-try cat /srv/lab/demo/file.txt
```

Остаёмся в `/srv/lab/demo`, он нужен дальше.

## 9. Права на каталоги: главная путаница

На каталогах права работают иначе, чем на файлах (см. таблицу в разделе 7). Проверим на опыте, где различие между `r` и `x`:

```bash
cd /srv/lab/demo
mkdir d
echo "inside" > d/f.txt
chmod 644 d
stat -c '%A %a %n' d
sudo -u lab-try ls /srv/lab/demo/d
sudo -u lab-try cat /srv/lab/demo/d/f.txt
```

У каталога `d` права `rw-r--r--`: есть `r`, но нет `x`. Результат: `ls` показывает имя `f.txt` (читать список можно), а `cat` отвечает `Permission denied` (зайти внутрь нельзя).

Теперь наоборот:

```bash
chmod 711 d
stat -c '%A %a %n' d
sudo -u lab-try ls /srv/lab/demo/d
sudo -u lab-try cat /srv/lab/demo/d/f.txt
```

Права `rwx--x--x`: у остальных есть `x`, но нет `r`. Результат: `ls` отказывает (список смотреть нельзя), а `cat` по точному имени **работает**.

Выводы, которые стоит запомнить:

- Чтобы **дойти** до файла, нужно право `x` на **каждый** каталог в пути: `/srv`, `/srv/lab`, `/srv/lab/demo`, и так далее.
- Чтобы **удалить или создать** файл в каталоге, нужны `w` и `x` **на каталоге**. Права на сам файл здесь вторичны.
- Типичный сбой: файл с правильными правами лежит в каталоге с `700`, и служба до него не доходит.

### Инструмент `namei`

`namei -l ПУТЬ` показывает права на **каждый** уровень пути. Незаменим при поиске причины `Permission denied`:

```bash
namei -l /srv/lab/demo/d/f.txt
```

Вывод построчно покажет `/`, `srv`, `lab`, `demo`, `d`, `f.txt`, и ты увидишь, где обрывается доступ.

## 10. Особые случаи: setgid, sticky bit и umask

### setgid на каталоге

Обычно новый файл получает **основную группу создавшего**. Для общих папок команды это неудобно: файл разработчика 1 принадлежит его личной группе, и разработчик 2 не может его править. Решение: бит **setgid** на каталоге. Тогда **новые файлы внутри наследуют группу каталога**.

```bash
chmod g+s КАТАЛОГ
```

В `ls -l` это видно по букве `s` на месте `x` у группы: `drwxrws---`. В числах первым добавляется цифра `2`: `2770`.

### sticky bit

Бит `t` на каталоге разрешает удалять в нём файлы **только их владельцам**. Классический пример `/tmp`:

```bash
ls -ld /tmp
```

Увидишь `drwxrwxrwt`: все могут писать в `/tmp`, но чужие файлы удалять нельзя.

### SUID (для общего понимания)

Бит `s` у владельца (`-rwsr-xr-x`) заставляет программу запускаться с правами **владельца**, а не запустившего. Так работает `/usr/bin/passwd`: обычный пользователь меняет пароль, хотя файл с паролями принадлежит `root`.

```bash
ls -l /usr/bin/passwd
```

Бит SUID опасен и применяется редко. Просто знай, что он существует.

### umask: какие права получает новый файл

Новые файлы создаются с «базовыми» правами (`666` для файлов и `777` для каталогов), из которых **вычитается маска** `umask`:

| umask | Файл получает | Каталог получает |
|---|---|---|
| `022` | `644` | `755` |
| `002` | `664` | `775` |

```bash
umask
su - lab-try -c umask
```

У `root` обычно `0022`, у обычных пользователей в Ubuntu `0002`. Поэтому файл, созданный обычным пользователем, по умолчанию доступен на запись его группе. Именно на этом построен кейс про общую папку.

## 11. sudo: права администратора по необходимости

Работать постоянно под `root` опасно: любая опечатка выполняется с максимальными правами. Принятая практика: работать обычным пользователем, а отдельные команды выполнять с правами администратора через **`sudo`**.

| Команда | Что делает |
|---|---|
| `sudo КОМАНДА` | выполнить команду от имени `root` |
| `sudo -u ИМЯ КОМАНДА` | выполнить от имени другого пользователя |
| `sudo -l` | показать, что **мне** разрешено |
| `sudo -l -U ИМЯ` | показать, что разрешено **пользователю** (запускает root) |
| `sudo -n КОМАНДА` | не спрашивать пароль, а сразу отказать (удобно для проверок) |

В Ubuntu все участники группы **`sudo`** могут выполнять любые команды. Поэтому «дать пользователю админские права» значит `usermod -aG sudo ИМЯ`.

### Тонкая настройка прав в /etc/sudoers.d

Иногда нужно разрешить **одну конкретную команду**, а не всё. Для этого пишут правила. Файл `/etc/sudoers` руками **не редактируют**: опечатка может сломать `sudo` для всех. Используют специальный редактор `visudo`, который проверяет синтаксис перед сохранением. Свои правила кладут в отдельные файлы в `/etc/sudoers.d/`:

```bash
visudo -f /etc/sudoers.d/ИМЯ_ФАЙЛА
```

Откроется `nano`. Формат правила:

```
пользователь  ХОСТ=(от_чьего_имени)  [NOPASSWD:]  /полный/путь/к/команде [аргументы]
```

Пример: пользователь `lab-ops` может от имени `root` без пароля смотреть статус одной службы:

```
lab-ops ALL=(root) NOPASSWD: /usr/bin/systemctl status ssh
```

Что важно знать:

- Команда указывается **с полным путём** (`/usr/bin/systemctl`). Найти путь можно через `which systemctl`.
- Если указаны **аргументы**, разрешена **только** такая точная комбинация. Команда `systemctl status cron` под это правило уже не подпадает.
- `NOPASSWD:` убирает запрос пароля. Для узких безопасных команд это нормально, для широких нет.
- Не пиши `ALL` вместо команды, это отдаёт все права. Это нарушение принципа наименьших привилегий.
- Файл правил должен иметь права `440` и принадлежать `root:root`. `visudo -f` выставит их сам.
- Проверка синтаксиса всех файлов: `visudo -c`.

На рабочих серверах перед правками `sudo` всегда держат **вторую открытую сессию** под `root`: если сломаешь `sudo`, будет чем починить.

## 12. Как искать причину Permission denied

`Permission denied` самая частая ошибка в работе. Действуй по плану, а не наугад:

1. **Кто запускает?** Определи пользователя, под которым работает программа (`id ИМЯ`). Для служб это отдельный служебный пользователь, не ты.
2. **Что именно запрашивается?** Какой путь и какое действие: прочитать, записать или запустить.
3. **Права на сам файл:** `ls -l ФАЙЛ`.
4. **Права на весь путь:** `namei -l ПОЛНЫЙ_ПУТЬ`. Нужен `x` на каждом каталоге.
5. **Проверь от имени нужного пользователя:** `sudo -u ИМЯ cat ФАЙЛ` (не под `root`: он всё обходит).
6. **Чини минимально.** Сначала подумай о владельце и группе, потом о режиме. Никогда не `777`.
7. **Проверь результат и проверь «от противного»:** программа теперь работает, **а посторонний пользователь (`nobody`) по-прежнему не имеет доступа**.
8. **Запиши**, что нашёл и что сделал. Это и есть отчёт.

> [!TIP]
> Если права в порядке, а ошибка осталась, причина может быть не в правах: например, неверный формат файла (кейс про `deploy.sh`), запрет запуска с диска или защита AppArmor. Об этом мы будем говорить в следующих уроках. Но почти всегда `Permission denied` в прикладных задачах это именно права.

## 13. Как поступают профессионалы

- Каждая служба работает **под своим служебным пользователем**, не под `root`.
- Секреты (пароли, ключи, токены) хранятся с правами `600` или `640` и принадлежат нужной группе.
- Общие каталоги команды: отдельная группа и `setgid`.
- Не работают под `root`: у каждого человека личная учётная запись и `sudo`.
- Права на `sudo` дают **узко и точно**, с полными путями.
- Не лечат проблему чужими правами `777`. Находят причину.
- После исправления проверяют **и** что нужному пользователю можно, **и** что посторонним нельзя.
- Любое изменение прав документируют: что было, что стало и почему.

| Что сделать | Команда |
|---|---|

| Создать служебного | `adduser --system --group --no-create-home ИМЯ` |

| Добавить в группу | `usermod -aG ГРУППА ИМЯ` (с `-a`!) |

| Войти как другой | `su - ИМЯ` |
| Удалить пользователя | `deluser --remove-home ИМЯ` |
| Права числом и буквами | `stat -c '%A %a %U:%G %n' ФАЙЛ` |
| Сменить права | `chmod 640 ФАЙЛ`, `chmod u+x ФАЙЛ` |
| Сменить владельца и группу | `chown ВЛАДЕЛЕЦ:ГРУППА ФАЙЛ` |
| Бит setgid на каталог | `chmod g+s КАТАЛОГ` |
| Права по всему пути | `namei -l ПУТЬ` |
| Проверить от имени пользователя | `sudo -u ИМЯ КОМАНДА` |
| Что разрешено пользователю | `sudo -l -U ИМЯ` |
| Правила sudo | `visudo -f /etc/sudoers.d/ИМЯ`, проверка: `visudo -c` |
| Искать в тексте | `grep -n "СЛОВО" ФАЙЛ`, `grep -c`, `grep -v` |

## 15. Проверь себя

Ответь **сам, до подсказок**:

1. Что означает `-rwxr-x---` и какое это число?
2. Зачем в команде `usermod -aG` нужна опция `-a`?
3. Что значит право `x` на каталоге? Чем оно отличается от `r`?
4. Почему проверять доступ под `root` бессмысленно?
5. Как узнать, на каком именно каталоге в пути обрывается доступ?
6. Для чего нужен бит `setgid` на общей папке команды?
7. Почему правило `lab-ops ALL=(root) NOPASSWD: ALL` плохое?
8. Какие права подойдут файлу с паролем базы данных, если его читает служба из группы `app`?

<details>
<summary>Ответы (открывай после того, как ответил сам)</summary>

1. Владелец: чтение, запись, запуск. Группа: чтение и запуск. Остальные: ничего. Число `750`.
2. Без `-a` группы пользователя **заменяются**, а не добавляются: он молча теряет все остальные, включая `sudo`.
3. `x` позволяет заходить в каталог и обращаться к файлам по имени. `r` позволяет смотреть список имён. Можно иметь одно без другого.
4. `root` игнорирует права, поэтому «работает под root» не доказывает, что будет работать у нужного пользователя.
5. `namei -l ПОЛНЫЙ_ПУТЬ`.
6. Новые файлы в папке наследуют группу папки, а не основную группу создавшего. Тогда все участники группы смогут их править.
7. `ALL` разрешает все команды без пароля, то есть полный доступ администратора. Нарушен принцип наименьших привилегий.
8. Например, владелец `root`, группа `app`, режим `640`: служба читает, посторонние нет.
